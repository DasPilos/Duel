# Сервер и клиент

## Настройки (`server/config.py`)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | `postgresql://game@127.0.0.1:5432/game` | PostgreSQL DSN. Пароль — в pgpass, не в коде |
| `DB_POOL_MIN_SIZE` / `DB_POOL_MAX_SIZE` | `1` / `20` | Размер пула соединений |
| `WORLD_ID` | `1` | Мир, обслуживаемый процессом Башни/Экономики; должен существовать в БД |
| `HOST` / `PORT` | `0.0.0.0` / `8765` | Адрес прослушивания |
| `SERVER_TIMEZONE` | `Europe/Kyiv` | Часовой пояс игрового времени |
| `CITY_TICK_INTERVAL_SECONDS` | `1` | Период фонового тика города |
| `CITY_CATCHUP_HOURS_PER_PASS` | `168` | Сколько часов города догоняется за один проход |

Для локальной разработки привязывайте сервер к `127.0.0.1`, чтобы он не был доступен из сети.

## Запуск

```powershell
$env:HOST = '127.0.0.1'; $env:PORT = '8765'
python -m server.central_main
```

Центральный сервер не привязан к игровому миру: аккаунт и lobby доступны, даже если список миров пуст. Проверка: `http://127.0.0.1:8765/health`.

Игровые миры запускаются отдельными процессами после центрального сервера. Tower использует `python -m tower.server.main`, Economy — `python -m economy.server.main`, каждый с собственными `WORLD_ID`, `GAME_SCHEMA` (`tower` или `economy`) и портом. Deck использует `python -m deck.server.main` с `DECK_WORLD_ID` и `DECK_PORT`. Центральный сервер выбирает entrypoint и выставляет соответствующую схему; процесс проверяет режим мира перед запуском. У каждого мира ровно один режим в `worlds.mode`.

Опциональный WebSocket-чат запускается отдельно: `python -m server.realtime` (нужен пакет `websockets`). Без него клиент использует HTTP.

## Клиент

Основной клиент — Godot (`godot_client/`, Godot 4.7.1). Откройте `godot_client/project.godot` и нажмите F5. Адрес сервера вводится на экране входа. Перед входом клиент проверяет `/api/version` и не пускает при несовместимой версии.

Python-клиент (Pygame) остаётся резервным и не поддерживает Front Line:

```powershell
python main.py --online --server http://127.0.0.1:8765
```

Переход оператора на Godot: `docs/CLIENT_MIGRATION_OPERATOR2.md`.

Адрес сервера задаётся флагом `--server`. Не используйте рабочий сервер при тестировании функций, которые меняют данные.

## API

Центральный API (`server/central_main.py`): `/health`, `/api/register`, `/api/login`, `/api/sessions/disconnect`, `/api/modes`, `/api/worlds`, `/api/lobby`, `/api/lobby/chat`, `/api/me`, `/api/account/password`, а также административные операции создания и запуска миров. Центральные `/api/map/catalog`, `/api/map/assets/...`, `/api/map/saved`, `/api/map/editor/saved` и `/api/map/editor/saved/<id>` позволяют модераторам сохранять и повторно открывать черновики без опубликованного или запущенного игрового мира; запросы редактора карт принимают тело до 16 MiB. Лобби-чат хранит последние 48 часов, ограничивает историю 100 сообщениями на запрос и применяет общий лимит частоты сообщений; смена пароля требует текущий пароль и завершает остальные центральные сессии аккаунта. Публикация карты в выбранный мир проверяет совпадение режима карты и мира. Deck управляет картами через собственный API режима.

Редактор может сохранять карты с режимом `front_line`, и сервер выдаёт их отдельно через `/api/map/saved?mode=front_line`. Front Line использует отдельный runtime на Tower-схеме. После 120-секундного ожидания сервер загружает первую сохранённую карту и открывает 60-секундный драфт класса и стартовых характеристик; доступны воин, лучник и маг, а для не подтвердивших выбор сервер случайно назначает один из этих классов. Спрайт героя первого уровня соответствует выбранному классу; асасин отображается в интерфейсе, но пока недоступен. По завершении первого драфта игроки переносятся на точки героя карты и получают отдельные 60 секунд свободной подготовки к волне. У каждой точки мобов Front Line есть собственная цель: основная цель карты, персонажи или оба варианта; в последнем случае моб выбирает более близкую цель. Эта настройка не используется другими режимами. Мобы не появляются и спаунеры не работают до окончания паузы. API `POST /api/front-line/character-draft` доступен только runtime Front Line.

Игровые API независимы: `tower.server.api`, `economy.server.api` и `deck.server.main` обслуживают только свой режим. Общий `server.mode_api` задаёт HTTP-механизм общих маршрутов и запуска режимных обработчиков; Tower- и Economy-маршруты реализованы в соответствующих API-модулях.

### Проверка версий

Центральный, Tower, Economy и Deck API без авторизации отвечают на `GET /api/version`. Клиент передаёт `app=client` или `app=editor`, `version` в формате `major.minor.patch` и номер `protocol`. Ответ содержит версии сервера и протокола, минимальные версии клиента/редактора, `build_id` и результат `compatibility`. Если приложение ниже минимальной версии или использует другой протокол, вход блокируется до обновления. Версия клиента Godot и протокол задаются в `godot_client/scripts/api_client.gd` (`CLIENT_VERSION`, `PROTOCOL_VERSION`). Python-клиент версию не передаёт, поэтому сервер для него совместимость не проверяет. Серверная политика минимальных версий и версия сервера — в `server/build_info.py`. Файла `client/build_info.py` в проекте нет.

- Сервис: `/health`, `/api/server/status`, `/api/server/restart-notice`, `/download/client`.
- `/api/server/status` отдаёт `build_id` — хэш `.py`-файлов `server/`, `core/` и `combat/` (`server/build_info.py`). Клиент сравнивает его при переподключении: если сборка сменилась, показывается «Клиент устарел».
- Вход и регистрация (`/api/login`, `/api/register`) выполняются только центральным сервером. После выбора мира клиент вызывает центральный `/api/worlds/<id>/connect`, который выдаёт токен сессии, ограниченный выбранным миром. Миры принимают только этот токен и не получают пароль игрока.
- Персонажи: `/api/characters` (`POST` принимает `name`, `profession_type` и необязательное `stats`: абсолютные значения характеристик, каждая не ниже 3, сумма потраченных очков не больше 3; выносливость фиксирована в 4), `/api/character/buy_drink`, `/api/character/use_drink`.
- Меню аккаунта: центральные `/api/modes`, `/api/worlds` (список с `mode`, `opens_at`, `closes_at`, `server_url`, `is_open`), `/api/lobby` (активные аккаунты), `/api/lobby/chat` (GET история, POST сообщение) и `/api/account/password` (смена пароля). Сессия центрального входа не привязана к игровому миру; при входе в выбранный мир клиент отдельно подключается к его адресу.
- Мир: `/api/map/terrain`, `/api/world/traveling-citizens`, `/api/world/traveling-convoys`.
- Редактор карт (только модераторы): черновики хранятся локально в `map_drafts/` у художника, сервер их не знает. Для Tower/Economy `POST /api/map/editor/saved` сохраняет заготовку, `GET /api/map/saved` перечисляет их, `GET /api/map/palette` читает общую палитру, а `POST /api/map/palette/preview` и `/apply` проверяют/применяют её изменения. `POST /api/map/editor/publish` с телом `{"cells": [{"layer","x","y","key"}], "world_id", "name", "map_w", "map_h"}` заменяет опубликованную карту мира в `map_live_cells` и `map_world_publish`; режим карты обязан совпасть с режимом выбранного мира. Одна и та же карта может быть опубликована на нескольких мирах. Слои `ground`, `overlay`, `infra`, `object`: `infra` (инфраструктура) лежит поверх прозрачных тайлов и земли, поэтому в рельефе перекрывает их под собой. После публикации сервер заменяет terrain мира «Башня» на опубликованную карту без перезапуска: apply_published_map в server/main.py переводит клетки через terrain_from_cells (server/map_editor.py) и вызывает world_map.apply_live_terrain, номер версии растёт (map.version в /api/map/terrain, terrain_version в снимке мира). Клиент видит новую версию в снимке и перечитывает terrain. Игроки и мобы внутри новых препятствий сдвигаются к ближайшей свободной точке. Трава и декор не передаются клиенту, пустая карта возвращает процедурный мир.- Город: `/api/city/structures`, `/api/buildings/...`, `/api/castle/...`, `/api/forge/...`.
- Инвентарь: `/api/inventory/...`, `/api/equipment/...`, `/api/storage/...`.
- Общая палитра карт (модераторы): `GET /api/map/palette` читает версию и настройки, `POST /api/map/palette/preview` проверяет переносы, `POST /api/map/palette/apply` повторно проверяет пароль и переносит тайлы во всех сохранённых картах и опубликованных мирах. Если перенос создаёт столкновение в целевом слое, сохраняется уже находившийся там тайл, а перемещённый удаляется; клиент предупреждает о каждом удалённом элементе после применения. Позиции хранятся только для перемещённых тайлов как `palette_position: {"x": 0, "y": 0}` относительно раздела в сетке шириной 10 тайлов; исходный порядок и пустые клетки сохраняются, а смену раздела задаёт свойство `palette_group`. Публикация новых версий мира запускает горячую синхронизацию опубликованной карты; процесс сервера не перезапускается.
- Создание карты в редакторе: ширина и высота настраиваются отдельно значениями 64, 128, 256, 512, 1024 и 1600 тайлов. Сервер принимает размеры до 1600 тайлов по каждой стороне; старые карты меньшего размера остаются совместимы.
- Социальное и чат: `/api/social/...`, `/api/chat/...`.

Экономические маршруты `/api/buildings/...`, `/api/forge/...`, `/api/castle/...` и передвижение жителей доступны только API Экономики. Башня не обслуживает их; Economy не обслуживает боевые `/api/world/sync`, `/api/world/leave` и `/api/world/corpse/loot`. Графические ассеты/каталог тайлов общие, но игровые правила для визуальных объектов принадлежат режиму. Очки вселенной и режимные рейтинги пока являются будущей заглушкой, начисления и хранение не реализованы.

Управление аккаунтами/лобби находится в `server/central_main.py`; режимные маршруты задаются отдельно в `tower/server/api.py`, `economy/server/api.py` и `deck/server/main.py`.

## Хранение

- PostgreSQL хранит центральные аккаунты, сессии, реестр миров и общие данные редактора в `public`. Игровые таблицы Tower, Economy и Deck находятся в отдельных схемах с теми же именами. Подключение процесса мира устанавливает `search_path` на его схему, а также на `public` для центральных таблиц.
- Миграция `0078_mode_database_schemas.sql` переносит старые игровые таблицы из `public` в `tower` и создаёт структуру `economy`; её запускает центральный сервер до старта игровых процессов. Будущие центральные миграции размещаются в `server/migrations/central/`, миграции режимов — в `server/migrations/modes/<режим>/`. Общие исходные миграции остаются в `server/migrations/`.
- Схемы, процессы и внешние API режимов разделены. Общий `server.main` содержит только общие API/HTTP-помощники и жизненный цикл процесса; сервисы Economy находятся в `economy/server/`, боевая логика Tower — в `tower/server/`. Общая карта и визуальные каталоги используются несколькими режимами без передачи им общих игровых правил.
- Состояние боя на карте мира в БД не хранится.

## Публикация клиента

Клиентский пакет — архив Python-клиента (Pygame) с исходниками и ресурсами, не исполняемый файл. Godot-клиент (`godot_client/`) в архив не входит и передаётся через репозиторий или копию папки проекта:

```powershell
python scripts/build_client_package.py
Get-FileHash client_package.zip -Algorithm SHA256
```

Архив создаётся в корне проекта и отдаётся сервером по `/download/client`. Он не версионируется в git. Пересоберите его после изменений клиента или ассетов.
Сборщик включает клиентский модуль `deck/` и исключает устаревшие карточные модули из корневых `combat/`, `scenes/` и `ui/`. Карты и состояние мира остаются в PostgreSQL; `cards.sqlite3` в клиентский архив не входит.

## Развёртывание

1. Проверьте локально: `python -m unittest discover -s tests -q` и `git diff --check`.
2. Опубликуйте проверенный коммит на GitHub.
3. На сервере обновите код только fast-forward (`git pull --ff-only`), не трогая файлы окружения и локальные runtime-файлы.
4. Проверьте синтаксис изменённых модулей (`python -m py_compile ...`).
5. Перезапустите сервис сервера и проверьте `/health`.

Клиентские изменения требуют нового `client_package.zip`. Серверные изменения требуют перезапуска сервера. Не копируйте локальные данные PostgreSQL на сервер, а продуктивные учётные данные не храните в репозитории.

## Монитор сервера (`ops/monitor.py`)

`ops/monitor.py` — локальная терминальная панель только для чтения. Она не открывает HTTP-порт и не отображает учётные данные. Показывает доступность API, состояние сервиса и PostgreSQL, онлайн-игроков, загрузку CPU, память, диск, сеть, время и ошибки журнала.

Ручная проверка на Linux-хосте:

```bash
cd <путь-к-проекту>
<venv>/bin/python -m ops.monitor --once
```

Установка на отдельную консоль (`tty2`): `sudo bash deploy/monitor/install.sh`. Пользователю нужна группа `adm` для чтения журнала. Установка не трогает сервис игры. Возврат к обычной консоли: `sudo systemctl disable --now game-monitor.service` и `sudo systemctl enable --now getty@tty2.service`.

Тесты разбора данных: `python -m unittest tests.test_server_monitor -q`.
