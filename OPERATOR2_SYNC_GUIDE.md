# Синхронизация копии игры Оператора 2

Это руководство помогает получить ту же **версию исходного кода и настройки правил**, что и у Оператора 1, и отдельно проверить, что клиент подключен к нужному серверу и миру. Git синхронизирует файлы проекта, но не PostgreSQL, параметры запуска, сохранения или уже запущенный клиент.

## Важно: что опубликовано сейчас

Базовая опубликованная ревизия, от которой подготовлена эта работа, — `7e8df78` (`Release shared city production and transport systems`). Она не содержит цепочку улучшений лесопилки, миграцию `server/migrations/0045_lumber_camp_upgrade_chain.sql` и этот runbook. Полный снимок уже опубликован в ветке `operator2-sync-2026-10-09`. Получайте именно эту ветку и сверяйте SHA; не ориентируйтесь на старую базовую ревизию или незакоммиченную локальную копию Оператора 1.

## Что именно синхронизировать

Ветка `operator2-sync-2026-10-09` уже опубликована. Оператор 1 должен передать точный SHA текущего commit; Оператор 2 получает её из чистого клона:

```powershell
git fetch origin
git switch --create operator2-sync-2026-10-09 --track origin/operator2-sync-2026-10-09
git rev-parse --short HEAD
```

Полученный SHA должен совпасть с сообщённым SHA. Если ветка уже есть локально, сначала проверьте `git status` и сохраните свои изменения; не перезаписывайте их.

| Часть | Как переносится | Что не переносится автоматически |
|---|---|---|
| Исходники и правила игры | Git commit из общего репозитория | Незакоммиченные файлы и локальные ветки |
| Схема PostgreSQL | SQL-файлы `server/migrations/`; сервер применяет новые миграции при старте | Пользовательские строки, уровень города, запасы и казна |
| Настройки сервера | Переменные окружения и `server/config.py` | `DATABASE_URL`, секреты и локальная конфигурация |
| Клиент | Запуск исходников из нужного commit либо новая сборка клиента | Уже запущенное окно и старый `client_package.zip` |
| Состояние мира | База выбранного сервера, `WORLD_ID` и фракция | Git не копирует состояние мира между базами |

Для одинаковой **версии игры** достаточно одинакового опубликованного commit. Для одинакового **состояния мира** оба клиента должны обращаться к одному и тому же серверу/миру либо к отдельно подготовленной тестовой базе. Не копировать production-базу и не передавать пароли.

## Возможности текущего снимка

После checkout нужного commit у Оператора 2 должны быть те же исходники и правила:

- Общее состояние города: население, сытость, назначения на работу и поездки; свободные жители и свободные рабочие слоты обрабатываются отдельно.
- Общее производство: продукция работников попадает в общий склад здания, личных долей урожая нет; снятие ограничивается вместимостью рюкзака.
- Прогрессия фермы: уровень 1 — склад 500 и два места; «Самозахват» добавляет место, плуг даёт +5%; оба улучшения открывают уровень 2 со складом 800 и вторым полем; пай и рукоять доступны на уровне 2, бонусы скорости складываются до +13%.
- Перевозки: общие повозки, маршруты, обслуживание и износ; работающая повозка расходует древесину, ремонт оплачивается древесиной.
- Корректный выход: клиент запускает уведомление сервера об отключении одновременно с затемнением и отсчётом 5→0; окно закрывается после завершения отсчёта и ответа сервера.
- Ограничение карты и ресурсов: сервер открывает загородные строения, дороги и ресурсы по уровню города из таблиц ниже.
- Цепочка лесопилки в этом снимке: расширение — 50 серебра/40 минут; усиленная рукоять — +8%, 70 серебра/60 минут; уровень 2 требует оба улучшения и стоит 50 серебра + 300 древесины/140 минут. Серебро берётся из казны, древесина — с общего склада.

Если какого-то пункта нет после обновления, сначала сравните SHA и серверный адрес. Не переносите отдельные Python-файлы вручную: сервер, клиент, миграция и тесты должны быть из одной ревизии.

## 1. Проверить локальную копию до обновления

Откройте PowerShell в корне репозитория Оператора 2 и выполните:

```powershell
git remote -v
git status --short --branch
git branch --show-current
git rev-parse --short HEAD
git fetch origin
git rev-parse --short origin/main
git log -5 --oneline --decorate
```

Проверьте, что `origin` указывает на общий репозиторий `https://github.com/DasPilos/Duel.git`, а нужный commit действительно находится в `origin/main` или в согласованной feature-ветке.

- Если `git status` показывает изменения, **не обновляйте копию вслепую**. Сначала сохраните собственную работу в своей ветке/commit или попросите помощи. Не используйте `git reset --hard`, `git clean -fd` и не удаляйте файлы ради синхронизации.
- Если рабочая копия чистая, обновляйте `main` только fast-forward:

```powershell
git switch main
git pull --ff-only origin main
git rev-parse --short HEAD
git status --short --branch
```

Последняя команда должна показать ожидаемый опубликованный SHA и чистую рабочую копию. Если `pull --ff-only` отказал, остановитесь и передайте Оператору 1 вывод команд проверки; не разрешайте конфликт случайным merge или reset.

Если репозитория ещё нет, сначала получите подтверждение, что нужный commit уже опубликован, затем клонируйте:

```powershell
git clone https://github.com/DasPilos/Duel.git
git -C Duel log -1 --oneline --decorate
```

Не переносите проект заменой папки поверх существующей: там могут быть собственные изменения, настройки и данные.

## 2. Установить зависимости и выбрать сервер

Проект рассчитан на Python 3.13 и Pygame 2.6. В корне новой копии:

```powershell
py -3.13 --version
py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Для локальной разработки сервер должен использовать отдельную development-БД PostgreSQL. В `DATABASE_URL` укажите локальную БД; пароль держите в `%APPDATA%\postgresql\pgpass.conf`, а не в Git, документации или команде запуска. Пример запуска локального сервера:

```powershell
$env:HOST = '127.0.0.1'
$env:PORT = '8765'
$env:WORLD_ID = '1'
$env:DATABASE_URL = 'postgresql://game@127.0.0.1:5432/game'
$env:DATABASE_URL = 'postgresql://game@127.0.0.1:5432/game'
python -m server.main
```

Миграции применяются сервером при старте. Убедитесь, что запуск завершился без ошибки подключения к PostgreSQL, затем проверьте:

```powershell
Invoke-RestMethod http://127.0.0.1:8765/health
```

Во втором PowerShell-окне, из корня того же commit, запустите клиент с явным сервером:

```powershell
.\.venv\Scripts\Activate.ps1
python main.py --online --server http://127.0.0.1:8765
```

Если `--online` опущен, клиент работает не в ожидаемом online-режиме. Адрес `http://192.168.1.230:8765` используйте только когда намеренно подключаетесь к общему серверу Z440 из доступной ему сети. Обновление файлов на компьютере Оператора 2 само по себе не обновляет Z440; серверный commit должен быть отдельно развернут и служба перезапущена. Если распространяется ZIP-клиент, его нужно пересобрать из того же SHA и скачать заново.

## 3. Проверить мир и уровень города

Загородные постройки и дороги фильтруются сервером по `castle_level` в `city_population_state` для текущих `WORLD_ID` и фракции. При разных `DATABASE_URL` или `WORLD_ID` можно получить тот же код, но другой уровень города и другое состояние.

Для локальной базы проверьте состояние безопасным read-only запросом (подставьте правильные host/user/database; секрет вводите только через настроенный `pgpass`):

```powershell
psql -h 127.0.0.1 -U game -d game -c "SELECT world_id, faction, castle_level FROM city_population_state ORDER BY world_id, faction;"
```

В текущей конфигурации используется фракция `light`; стандартный `WORLD_ID` — `1`. Не меняйте уровень в production-БД ради визуальной проверки. Для теста используйте отдельный мир или disposable-БД.

## 4. Ожидаемая доступность по уровням

Это правила проекта, а не настройка клиента. На уровне города 1 правильное отображение **не должно** показывать все загородные здания и все дороги.

| Уровень города | Загородные постройки и дороги |
|---|---|
| 1 | `wheat_farm`, `lumber_camp` |
| 2 | Дополнительно `mountain_rift` |
| 3 | Дополнительно `barnyard` |
| 4 | Дополнительно `black_pit` |

Ресурсы городских хранилищ также открываются постепенно:

| Уровень | Амбар | Склад |
|---|---|---|
| 1 | Пшеница | Древесина |
| 2 | Дополнительно ягоды | Доски, лён, камень, железо, слитки железа, каменные блоки |
| 3 | Дополнительно мясо | Хлопок, кожа, плотная/толстая кожа, ткань |
| 4 | Без новых ресурсов амбара | Уголь, мифрил, обсидиан, сталь и самоцветы |

Источники правил: `core/city_progression.py`; фильтрация объектов: `server/structures.py`; фильтрация дорог: `server/world_roads.py`; передача уровня из БД в карту: `server/main.py` и `server/world_map.py`. API карты — `GET /api/map/terrain`.

## 5. Если у Оператора 2 видны все здания или дороги

Проверяйте по порядку:

1. Сверьте `git rev-parse --short HEAD` с SHA, который передал Оператор 1. Старый client ZIP или feature-ветка не равны нужному commit.
2. Убедитесь, что клиент запущен с правильным `--server`, а не подключен к другой локальной/production-базе.
3. На сервере проверьте `WORLD_ID` и `castle_level` SQL-запросом выше. Если уровень 4, полный список построек ожидаем.
4. Закройте клиент, перезапустите нужный сервер после обновления server-кода, затем откройте клиент снова. Сервер отвечает за `/api/map/terrain`; перезапуск только клиента не обновит устаревший сервер.
5. При `castle_level = 1` ожидаются только две постройки и два маршрута из таблицы уровня 1. Если не так, проверьте, что server и client действительно используют одну версию и один backend.
6. Запустите регрессионные проверки из корня репозитория:

```powershell
python -m unittest tests.test_world_terrain.WorldTerrainTests.test_city_level_filters_country_objects_and_roads -v
python -m unittest tests.test_production_buildings -q
```

Не исправляйте это удалением объектов вручную из карты: сначала установите, какое значение уровня и какой backend фактически использует клиент.
